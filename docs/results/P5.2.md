**Every measured number in this report is copied from a committed record** by a script
(the tables), or pasted from a command's output (the verification log). The records:

| Record | What | Command |

## 1. Summary

**What was unfair.** Two things, both in DCP's favour. (1) P5.1's OpenLineage baseline
lost recall because of **this repository's bridge**: it mapped one OpenLineage run per
(trace, process), so a consumer that joined two traces became two runs and OpenLineage's
core model (inputs × outputs per run) could not connect them. A real OpenLineage
integration reports one run per process. (2) The scaled benchmark never generated DCP's
two documented failure modes: a consumer that reads several records from one topic
(job-level parenting keeps the latest read per dataset), and a job that reads a table
another job wrote (Postgres reads carry no parents).

**What changed.** The bridge gained a `process` run scope (one run per process; the
default is unchanged), and every workload is now also scored against OpenLineage's core
model under it, in rows appended after every existing one. The generator (version 1.1)
gained the two failure-mode job kinds behind parameters that default to off, so every
existing key regenerates byte for byte; six stress keys exercise them, scored live and in
replay in their own section, with every miss explained by a named cause. Part C made the
repository release-ready (version 0.1.0, changelog, citation, packaging check, limitations
file, evidence pack, figures), and Part D closed v1: the final report
[`V1.md`](V1.md) and the owner's runbook [`RUNBOOK.md`](../RUNBOOK.md).

**The fair numbers.** Per process, OpenLineage's core model loses **no** expected item on
the scale keys, so its P5.1 recall loss was the bridge's; its precision stays far below
DCP's (§3). On the stress set, DCP's provenance recall drops below 1.0, every miss carrying
one of the two causes, while dataset-level lineage keeps full recall at lower precision: a
real precision-against-recall trade-off (§4).

**Reading.**

- **DCP's provenance recall drops below 1.0**, and every miss carries one of the two
  causes, each predicted from the key alone: most come from store-mediated reads (the
  Postgres read of a table carries no parents, so DCP's provenance stops at the table),
  the rest from multi-record consumers (the write is parented to the latest record only).
  DCP's nodes, dataset edges and run edges keep recall 1.0: each lost item is an upstream
  dataset *behind* an attested edge, never the edge itself. Every extra item is still a
  distractor read.
- **The precision-against-recall trade-off, plainly: on the stress set, dataset-level
  lineage beats DCP on recall.** Reachability over dataset edges crosses tables and
  follows every producer of a topic, so it keeps every expected provenance item, but at
  markedly lower precision than DCP's (the `dataset-level baseline` rows above, against
  `DCP run-level`). DCP's run-level provenance is precise about what it attests and silent
  about what it cannot attest; dataset-level lineage over-approximates and so never misses
  these. Which is preferable depends on the question: impact analysis wants recall (DCP's
  own `downstream` query is dataset-level for that reason), provenance wants precision.
- **OpenLineage's core model per process** keeps recall 1.0 here too, at the lowest
  precision of any method at the provenance level; under the trace × process mapping it
  loses items to split runs, some of them further upstream through a store read.
- **OpenLineage with the `dcp` facet equals DCP**, its recall loss included: the facet
  carries exactly DCP's events.
- The stress set is not pooled with the scale keys or the hand-written keys anywhere.
  Multi-record consumers are rare in it (`p_multi_record` is per consumer), so that cause's
  counts are small; the parameters were fixed before any stress key was scored.

## 6. What this changes for the paper

**Stronger.** The coverage claim and the accuracy claim stand unchanged, and the
comparison behind them is now fair: OpenLineage is modelled as it actually reports (one
run per process), and DCP's precision advantage over OpenLineage's core model holds under
that mapping at every level on the scale keys and the stress set. The paper can also say
that the benchmark measures DCP's own weaknesses rather than avoiding them: the stress set,
its per-cause table and the zero-unexplained checks are the evidence.

**Weaker.** OpenLineage's recall loss in P5.1 must not be cited as a weakness of
OpenLineage: per process it has none on these keys. DCP's own recall is no longer 1.0
everywhere: on workloads that pass data through a table, or merge several records of a
topic, DCP's provenance misses upstream items, and dataset-level lineage does not.

**New wording.** State the comparison as a trade-off, not a dominance: DCP's run-level
provenance is the most precise method measured and has recall 1.0 where data moves through
attested hops (the scale keys), and loses recall exactly where its hops are not attested
(store-mediated reads, multi-record consumers), where dataset-level lineage keeps recall at
lower precision. The OpenLineage comparison should name its mapping: "OpenLineage's core
model, one run per process". Every number for these sentences is in
[`docs/paper/evidence.md`](../paper/evidence.md) (C3, C4, C5).

## 7. Decisions made

- **Branch** `p5.2-fair-baselines`, from the latest `main` (`c84b859`), committed stage
  by stage in the task's order, each commit passing lint and the tests.
- **The run scope is an option, the default unchanged** (A1): `trace-process` stays the
  default everywhere (CLI, `to_openlineage`, every existing score), so every earlier
  export and number is unchanged; `process` is opt-in and scored in appended rows.
- **The per-process rows are printed in their own section** after each workload's
  existing sections, with a level column widened to fit their longer labels, so no
  existing line of `score.py`'s output changes (the existing tables keep their width).
- **The stress set lives in `benchmarks/ground_truth/stress/`**, a directory of its own,
  scored in its own section of the `scale` stage, never in `generated/`'s aggregates.
- **Every miss on the stress set is checked against a cause predicted from the key alone**
  (its truth and its `generated` block), never from DCP's output, so the check could fail.
- **The owner's single run gets its own fixed-cost record** (`render.py --fixed-cost`),
  so the evidence pack's throughput claim (C8) moves to the owner's machine with the rest.
- **The evidence pack takes, per claim, the newest record that has the claim's section**,
  and labels a `P5-local*.md` record as the owner's machine; the README's results block is

- **Docker was available in this sandbox** (not in P5.1's), so Postgres 16 and Kafka 3.8.0

## 8. Assumptions — needs review

Judgement calls made without asking; the more conservative option each time.

**Part A**

1. **The `process` runId name starts with the word `process`** (`process|host|pid|name`),
   while a `trace-process` name starts with a trace id; DCP emits trace ids as UUIDs, so
   the two cannot collide. A hand-made envelope whose `trace_id` is literally `process`
   could; the envelope schema does not forbid it.
2. **A `process` facet also carries each event's own `trace_id`** (optional in the schema),
   beyond the `trace_ids` list the task asked for: without it the round trip (A2 row 12)
   could not restore which trace each event belonged to.
3. **A2 row 14 is also checked on real capture output**: every hand-written key and every
   generated scale key, in both modes.

**Part B**

4. **`p_multi_record` is a probability per consumer**: a consumer becomes a multi-record
   consumer of 2-3 records from one topic, each from a different producer; if no topic has
   records from two producers, it stays an ordinary consumer.
5. **`p_store_read` is a probability per job slot other than a script** (scripts are the
   only producers, and consumers need records): the slot becomes a store-read job that reads
   one table an earlier job wrote (plus, with `p_distractor`, a distractor read) and inserts
   one row computed from it. When a table written by another store-read job exists, it is
   chosen with probability 1/2 (`P_STORE_CHAIN`), giving chains of length 2; never longer.
   If no written table exists yet, the slot keeps its kind.
6. **Version numbering.** `generate.VERSION` stays `"1.0"`: it is what a key with both new
   parameters off records, byte-identical to 1.0's output, and the existing pinned test
   compares the committed keys with it. The generator's own version, recorded by keys with
   either parameter on, is `GENERATOR_VERSION = "1.1"`.
7. **Stress keys are not in `generate.KEYS`**: the existing pinned tests require every key
   in `generated/` to be 30 jobs (or `scale_large`) at version 1.0. They are in
   `STRESS_KEYS`, in `stress/`, written and checked by the same `--write`/`--check`.
8. **Seeds 201-205 and 300**, chosen before generating; the parameters are the task's
   (0.15 and 0.25, the rest default). Nothing was changed after any score was seen.
9. **The split-run explanation on the stress set follows the truth upstream** through store
   reads (`scale.split_losses`): a split consumer loses provenance for every dataset
   downstream of what it wrote, including through a table. The scale keys keep P5.1's
   direct-writer rule unchanged (it explains every miss there).
10. **B2 row 10's live test is opt-in** (`DCP_TEST_LIVE=1`): it drops and re-creates
    `gen_*` tables and topics, so it must never run against the owner's database by
    accident. It ran here (item 1, item 4); the CI `live` job also runs a stress key live
    (`run.py --quick` runs `stress_s01`).

**Part C and D**

11. **F3-F5 come from a parsed record.** No raw JSON of an overhead run was ever
    committed, and new overhead runs are out of scope, so `figures.py` falls back to the
    newest committed overhead record (`P5-p51-after-final.md`), parsing its tables by code;
    each figure's footer says so. The owner's raw JSON replaces it (runbook step 6).
12. **The PyPI names were checked again** (P5.1 had recorded them a day earlier).
13. **Package READMEs were added** (`sdk-python/README.md`, `backend/README.md`) and
    declared as `readme` in all three `pyproject.toml` files, so `twine check` passes
    without warnings. Release metadata only.
14. **The bridge's `__version__` moved to `0.1.0` too** (it is outside `sdk-python/dcp/`
    and `backend/app/`); the version test checks it as well as the four the task names.
    **`backend/app/main.py` still passes `version="0.1.0.dev0"` to FastAPI**: it is not a
    `__version__` line, so P5.2 could not change it (a follow-up in `LIMITATIONS.md`).
