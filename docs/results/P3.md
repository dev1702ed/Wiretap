# P3 results: queryable lineage

Branch `p3-graph-backend`. Task spec: `docs/tasks/P3.md`.

## 1. Summary

P3 adds a backend that stores every DCP event in an append-only SQLite log and
builds a lineage graph from it. The graph can be rebuilt exactly by replaying the
log, and it gives the same answer for any arrival order. It answers run-level
provenance, dataset-level lineage and blast-radius queries over an HTTP API. The
SDK gains the two sinks that feed it: a JSONL file emitter, and an HTTP emitter
that never blocks the caller.

Both ground-truth workloads score 1.0 precision and recall at every level. On
`topic_fan_in`, the dataset-level baseline scores **2/3 precision** for
`daily_revenue`'s provenance, where run-level provenance scores 1.0. That is the
first measured evidence of what propagation adds. It comes from a replay with
faked I/O, not a live run.

## 2. What was built

|---|---|---|

It keeps an event graph (edge_id nodes, parent → child arcs) and a dataset graph (read dataset → write dataset). **Reading.** DCP's graph matches both answer keys exactly: nodes, dataset edges,
run edges and run-level provenance all score 1.0 precision and 1.0 recall.

On `dark_zone`, the baseline also scores 1.0. There is only one path, so matching
the topic name recovers everything, and propagation adds nothing measurable.

On `topic_fan_in`, the dataset-level baseline says `daily_revenue` derives from
`refunds` as well. Both producers wrote `enriched_orders`, so reachability over
dataset edges cannot tell them apart. It scores 2/3 precision, with `refunds` as
the false positive. Run-level provenance follows the parent carried in the
consumed record's `dcp-context` header back to `enrich_orders.py`'s write alone,
and scores 1.0. That matches the expectation in the task spec. Nothing was tuned
to reach it.

**Caveat, stated plainly.** These results replay DCP's real capture code
(`_capture`, `_on_produce`, `_on_consume`) with faked database and broker I/O: a
fake cursor that reports host, port and database, and fake Kafka messages that
carry the headers the producer's capture returned. They are **not live runs**.
Live replay against Postgres and Kafka is P5. The workloads are also small: two
answer keys, with 3 and 4 datasets.

## 5. Decisions made

**Identity: conservative resolution.** `resolve()` only makes changes that are
deterministic and lossless: it trims whitespace and lowercases the scheme and
host. It does not resolve DNS, does not canonicalise `localhost`, and does not
merge hosts or change name case.

- For this instrument, a false merge is worse than fragmentation. A false merge
  invents an edge that no later step can tell apart from an attested one, and it
  corrupts precision.
- Fragmentation fails visibly, as lower recall in a ground-truth score.
- The cost: a deployment that reaches one database through several host names
  will fragment.
- Full rationale: `docs/decisions/identity.md`.

**Emitter backpressure: never block, drop and count.** `HTTPEmitter.emit()` calls
`put_nowait` on a bounded queue. When the queue is full, the event is dropped,
`dropped` is incremented and a warning is logged.

- The P2 stub leaned towards blocking briefly first. `emitters/__init__.py` makes
  non-blocking a hard requirement for the < 1 ms p99 budget, so non-blocking wins.
- A dropped event disconnects the graph, so drops are counted exactly and never
  silent.
- Failed POSTs are retried with exponential backoff, then dropped and counted.
- `flush(timeout)` waits for the queue to drain, and `atexit` calls it, so a
  script that never calls `dcp.shutdown()` still delivers its events. A
  subprocess test checks this.

**Query parameters instead of path segments.** Dataset keys contain `://` and
`/`, so the API takes them as query parameters: `GET /upstream?namespace=&name=&level=`
and `GET /downstream?namespace=&name=`. **This deviates from the roadmap's
`GET /downstream/{dataset}`**. As path segments, the keys would need
percent-encoding that proxies and clients handle inconsistently.

**Run-level vs. dataset-level semantics.**

- `upstream(ds)` is run-level provenance. It starts from every write event on
  `ds`, walks `parent` links over events, and collects the dataset of every event
  it reaches. It never falls back to dataset-level reachability; a test checks
  that it stops at a table another job wrote.
- `dataset_upstream(ds)` is the dataset-level baseline, and the thing `upstream`
  is measured against.
- `downstream(ds)` is deliberately dataset-level, because impact analysis wants
  recall.
- All three exclude `ds` itself, so a self-loop (`UPDATE t … WHERE id IN (SELECT id FROM t)`)
  does not list `t` as its own ancestor.

**Order independence by set semantics.**

- The graph's state is a set of records per edge_id plus a set of parent arcs.
  Every arc links every record of the parent to every record of the child.
- When an event arrives, only arcs touching it are relinked. The result is
  therefore a function of the set of events, whatever their order.
- A test checks this over every permutation of the event set.
- A parent that has not arrived yet is a dangling node. It is linked when its
  event arrives, and it is reported until then.

## 6. Assumptions — needs review

Judgement calls the task file did not settle. In each case I took the more
conservative option.

**Branch and commit plan**

1. **The B8 flip landed with B1–B5, not with B7.**
   `test_graph_matches_answer_key` was `xfail(strict=True)`. Once the graph
   existed it passed, and a strict XPASS fails the run. The commit that added the
   graph therefore also removed the xfail and switched to `importorskip`, so that
   every commit passes its own tests. B7's tests and D1's harness came later.
2. **An extra commit between B7 and D.** It rejects a malformed `http://` port at
   `init()` and a `queue_size` or `batch_size` below 1: `Queue(maxsize=0)` is
   unbounded.

**Emitters**

3. **`HTTPEmitter` never blocks, overriding the stub's "block briefly".** The
   task asked for this to be recorded here.
4. **Drop warnings are rate-limited.** The drop count is exact, but a warning is
   logged only when the total crosses a power of two (1, 2, 4, 8, …). Logging
   every drop from the caller's thread under sustained overload would make
   logging the thing that blocks.
5. **4xx responses are not retried, except 408 and 429.** A rejected batch cannot
   succeed on retry. 5xx responses and network errors are retried.
6. **HTTP emitter defaults:**

   | Setting | Default |
   |---|---|
   | `queue_size` | 10,000 (from the stub) |
   | `batch_size` | 500 |
   | `max_retries` | 3 (0.5 s, 1 s, 2 s backoff) |
   | request timeout | 5 s |

   The worker sends whatever is queued, up to `batch_size`, without waiting to
   fill a batch.
7. **Delivery is at least once.** A POST that the backend stored but whose
   response was lost is retried, so the event is sent twice. The graph folds
   identical events once. The append-only log keeps both copies, and
   `event_count` counts distinct events.
8. **`https://` sinks raise `ValueError`.** The task lists only `http://`. Adding
   HTTPS is a one-line change once it is wanted.
9. **`file://` paths are taken literally.** Everything after `file://` is the
   path, verbatim: `file:///abs/path` is absolute and `file://rel.jsonl` is
   relative. There is no URL decoding.
10. **The file emitter flushes every line to the OS, without fsync.** A crashed
    script loses nothing it emitted, but a machine crash can.
11. **`init()` builds the new sink before changing any state.** A bad spec
    changes nothing. Re-initialising closes the previous sink, which flushes it
    first, and `shutdown` is registered with `atexit` only once.

**Backend and graph**

12. **`resolve()` returns a `(namespace, name)` tuple**, not the stub's `str`.
    The graph contract keys datasets by that tuple. The graph applies `resolve`
    in `add()` and in every query, and the API resolves query parameters the same
    way.
13. **Events that share an `edge_id` but differ are all kept.** A parent
    reference resolves to each of them. This is deterministic and
    order-independent, but it is not reported separately.
14. **An unknown dataset** gets empty sets from the graph and `404` from the API.
    A dataset that appears only in reads is still a dataset.
15. **The store is an `EventStore` class, not module-level functions.** This
    makes the path injectable. I added `append_many`, one transaction per batch,
    so a batch is atomic in storage as well as in validation.
16. **Ingest does not assert `format: date-time`.** It validates with
    `Draft202012Validator` exactly as the SDK's tests do. jsonschema's date-time
    check depends on an optional package, so enforcing it would make acceptance
    depend on the environment. `ts` is not used by the graph.
17. **The backend finds the schema at a repo-relative path**
    (`spec/envelope.schema.json`). It must run from a checkout or an editable
    install, which is what CI does.
18. **API responses:**
    - `POST []` returns `{"accepted": 0}`.
    - `POST /events` returns 200.
    - The `422` detail is a list of `{index, error}`, one per schema violation.
    - Malformed JSON, or a body that is neither an object nor an array, is `422`
      from FastAPI's own validation.
19. **One lock covers append-then-fold and every read of the graph.** Request
    handlers run in a thread pool, and networkx structures are not thread-safe.

**Other code changes**

20. **A7: dot counting.** A name is left unprefixed when it already has three or
    more dot-separated parts. Names are deduplicated again after qualification,
    so `orders` and `dcp.public.orders` in one statement are one read. A quoted
    identifier containing a dot would be miscounted (§7).
21. **The harness rejects unknown step types.** An unknown step in an answer key
    raises an error instead of being skipped silently. The old in-test replay
    ignored such steps.
22. **`score.py` always exits 0.** It is a report, not a gate: the gate is
    `test_graph_matches_answer_key`. When nothing is found, precision prints
    as `n/a`.

**Lint and tooling**

23. **The "extended rule set" is not configured anywhere.** Ruff's defaults in
    the installed version (0.16.9) provide it, including BLE001, S110, FURB,
    RUF022 and RUF100. CI installs `ruff>=0.4`, so a future ruff release could
    change the defaults and turn CI red without a code change. Pinning ruff is
    worth considering; I did not change it.
24. **`backend/` has no ruff config.** Its line length is therefore 88 (the SDK
    uses 100), and in `backend/tests` the `app` imports sort as third-party. I
    left the config alone.
25. **CI does not lint `benchmarks/*.py`.** The task's CI commands cover only
    `sdk-python` and `backend`. I linted and formatted `benchmarks/` locally with
    the same ruff, and it is clean. Adding it to CI is a one-word change.
26. **`backend/tests/conftest.py` shares its basename with
    `sdk-python/tests/conftest.py`.** Pytest imports conftest files specially,
    and running both directories in one invocation passes, so I kept it. Every
    test module name is unique.

**Docs updated beyond the task list**

27. So that no doc makes a stale claim, I also updated:
    - `benchmarks/ground_truth/README.md`: the "Tests" section and the answer-key
      naming caveat.
    - `benchmarks/adversarial/README.md`: cases 1 and 3 are no longer "xfail until
      P3", and the store-mediated line no longer says P3 infers that link.
    - The spec's status line.
    - `config.py`'s docstring.
28. **In `ROADMAP.md`, only P3 is marked ☑.** P0–P2 statuses are unchanged, since
    the task asked only for P3. The P3 deliverable text still reads
    `GET /downstream/{dataset}`; the deviation is recorded in §5.

**Environment**

29. **Branch.** The task environment named another development branch
    (`claude/nifty-hopper-ijtnf9`). The user's instruction named
    `p3-graph-backend`, which the task file also names, so that branch was used.

## 7. Known limitations and follow-ups

**Deliberately not built**

- **Store-mediated inference.** Job A writes a table and job B later reads it.
  That link is not attested, because rows carry no per-record metadata, and P3
  does not infer it.
  - Run-level `upstream` stops at the table. The dataset graph joins the two only
    through the shared table node.
  - Follow-up: infer these links as a separate, labelled edge class. Never mix
    them into attested edges, and score them separately.
- **An explicit identity alias map**, and Kafka cluster ID as namespace. Both are
  described in `docs/decisions/identity.md`.
- **Out of scope for P3:** the OpenLineage bridge, Marquez, docker-compose and
  live runs.

**Scale (prototype choices)**

- The graph is in memory and grows with every event ever ingested. `/graph`
  returns everything, with no pagination.
- `upstream` walks the whole history of every write to the queried dataset.
- The duplicate check holds each event's canonical JSON. That roughly doubles
  the memory held per event.
- **The backend must run as one process (one uvicorn worker).** Each worker
  would hold its own graph and fold only its own POSTs, although all of them
  write to the same log.
- One SQLite connection behind a lock caps ingest throughput.

**Emitters**

- Under sustained overload, events are dropped by design. The drops are counted,
  but they disconnect the graph.
- A `422` rejects the whole batch. One invalid event drops its batch-mates.
  The SDK only emits schema-valid events, so this should not arise from DCP
  itself.
- Losses the file sink does not have:
  - Events still queued when the process is killed (SIGKILL, `os._exit`) are
    lost.
  - Events emitted after the `atexit` handlers have run are lost.
- An HTTP emitter created before `os.fork()` has no worker thread in the child.
  The child's events are never sent, and they are not counted as dropped.
- No HTTPS, and no authentication, on the HTTP sink.
- Overhead is not measured. The non-blocking behaviour is tested, but the
  < 1 ms p99 claim still needs the P5 overhead benchmark.

**Capture limitations (unchanged)**

- Worker-thread reads do not parent later writes. This is the remaining xfail.
- Only the last record of a `consume()` batch parents later writes.
- `executemany`, `copy` and `SerializingProducer` are not intercepted.
- Kafka writes are attested at `produce()`, not at broker acknowledgement.
- A7 counts dots, so a quoted Postgres identifier containing a `.` can be
  mis-qualified.

**Noticed, left out of scope**

- `sdk-python/tests/test_propagation.py` still carries a commented-out
  `# @pytest.mark.xfail(reason="P2", strict=True)` above
  `test_kafka_header_roundtrip`. It is harmless, but it could be deleted.
- Starlette deprecates using `httpx` with its `TestClient` (the one backend test
  warning). The backend's dev dependencies may need `httpx2` once Starlette drops
  support.
- `CONTRIBUTING.md`'s "Dev setup" still installs only the SDK. The CI workflow
  shows the full setup.
