## 1. Summary

The three threats to validity named in the task are closed, and each found
something:

1. **The cache-miss path is now measured, and on P5's code it failed the
   latency target.** The new L tiers inline a different literal on every call,
   as ad-hoc scripts do. On P5's code (`p51-before-final`), L5 (the analytical
   query with one literal inlined) was "not met" for < 1 ms p99 added on every
   configuration that captures, and L1 and L3 were "met" or "inconclusive". After O1, the
   literal-normalised parse-cache key, **every tier, T and L, is "met" on every
   configuration** (§3). Throughput remains "not met".
2. **The per-call cost is attributed (§4).** The new `wrap-only` and
   `capture-null` configurations split it: DCP's wrapper alone costs close to
   nothing (its interval includes zero on most tiers); DCP's own **capture and event construction on the real psycopg
   path** is the largest component, several times what the CPU microbenchmark's
   fake cursor shows for the same function; asynchronous enqueue, the
   synchronous file write and the SQL comment are each smaller. That is the
   "unexplained ~40 µs": it is not in the sinks, it is capture itself on the
   real call path. The profile splits it into ID generation, timestamps,
   `connection.info` reads into libpq, and `_capture`'s own work, none of which
   dominates alone.
3. **The ground truth is no longer four toys (§8).** Eleven generated keys
   (ten of 30 jobs and one of 100), with truth derived from real data flow, run live and in replay with identical results. DCP's recall is
   1.0 everywhere; its precision drops below 1.0 exactly where its job-level
   parenting meets a distractor read, and every extra item it reports is such a
   read. The dataset-level baseline and OpenLineage's core model lose far more
   precision; with the `dcp` facet, OpenLineage matches DCP.

Two optimisations did not do what was hoped, and are reported as measured:
O2 (the per-connection namespace cache) removes the `connection.info` reads
from the profile but its effect on the timed cost is within the noise on most
tiers; and O3 (the asynchronous file sink) **made the file sink slower**, so
the synchronous sink is the default again (§5). Start-up under `dcp-instrument`
fell several-fold (§6). The < 2% throughput target is still not met on this
machine's sub-millisecond queries (§7).

### Naming the ~40 µs

On the owner's machine, `_capture` on a fake cursor costs 4.9 µs (T1, 4a), yet
`http-down` adds 50 µs to a real Postgres call. The same gap shows here: 4a's
`_capture` on T1 is 9.8 µs (Python 3.12, `P5-p51-before.md`), while the
attribution's **capture + construction** component, which is exactly the
difference between running `_capture` (with a discarding sink) and not
running it, on the real psycopg path, is +33.7 µs at p50. The wrapper itself
(`wrap-only`) is +1.1 µs, and asynchronous enqueue is +12.1 µs. So **the ~40 µs
is DCP's own capture and event construction, measured on the real call path**,
not the wrapper and not the sinks. The fake cursor understates it.

## 5. Optimisations

Each is its own commit, each was allowed only by A3's attribution (or, for O1,
the cache-miss path A2 measures), and each was checked to be output-identical:
the full test suites on Python 3.10, 3.12 and 3.14, the pinned replay output
(`backend/tests/test_backend_score.py`, byte for byte), every ground-truth
score in replay, hand-written and generated (`benchmarks/tests`), and, on the
final code, every live score ([`P5-p51-ground-truth-after.md`](P5-p51-ground-truth-after.md)
matches [`P5-p51-ground-truth.md`](P5-p51-ground-truth.md) row for row; only
the run-id lines differ). No optimisation changes any emitted field other than
`edge_id`, `trace_id` and `ts`, and none changes event order.

### O1: literal-normalised parse-cache key (commit "P5.1 A4 O1")

**Attribution:** the cache-miss path (§3, §4): before O1, capture +
construction on L1 is +358.5 µs at p50, almost all of it sqlglot.

**What:** the parse cache gains a second level. The exact-text level is
unchanged, so a parameterised query's hit path costs what it did in P5. On an
exact miss, one left-to-right pass replaces every literal (numbers, `''`
strings with `''` escapes, `E''` strings with backslash escapes,
dollar-quoted strings) with a placeholder and collapses lists of them; it
never touches identifiers, quoted identifiers, keywords or comments. The
result is looked up under that key; on a miss the **original** text is
classified, and the result is stored under the key only if sqlglot parsed it.
Text the pass cannot read for certain (an unterminated quote, a stray `$`, a
nested block comment) is its own key. Both levels are bounded to 1,024 entries.

**Output identity, tested** (`sdk-python/tests/test_classify_cache.py`):
normalised-key results equal direct classification across the corpus, every
answer key's SQL (hand-written and generated), and 3,000 randomised literal
variations of 14 statement shapes; quoted identifiers and dollar quotes survive
normalisation; 3,000 random pairs of statements differing only in identifiers
never share a key; a parse failure never decides for its siblings; both levels
are bounded.

**Before/after:** §3 (the L tiers) and the 4a tables. The T tiers' 4a capture
cost is unchanged by O1, as it should be: they hit the exact-text level.

### O2: per-connection namespace cache (commit "P5.1 A4 O2")

**Attribution:** capture + construction is the largest component at T1
(+33.7 µs, §4), and the profile puts the `connection.info` reads among its

that cannot be weakly referenced). A psycopg connection's host, port and

regular expression is compiled on the first exact-text miss, and `import dcp`
resolves its five public names on first use (PEP 562), so the `dcp-instrument`
wrapper process no longer loads the interceptors. A program that does import
both libraries still pays for them (the last row), as it does without DCP;
what remains is DCP's own modules and the second interpreter.

tests pass unchanged; a program that never imports psycopg or confluent-kafka

module keeps its real loader; a patch that fails never breaks the import; a
library already imported at start-up is patched at once; `import dcp` loads

**What it means for the < 2% target.** The target is a percentage, so whether
DCP meets it depends on the query, not only on DCP. This sandbox's queries are
sub-millisecond round trips to a local server, and against them every fixed

met" or "inconclusive", before and after. The table shows the other side: at a
1 ms query every configuration still loses more than 2%; at a 10 ms query
every configuration of every T tier, L1 and L3 loses less than 2%, and L5 (the
cache-miss analytical query) does not; at 100 ms every row does. A paper should state the throughput result in these terms, as
the fixed cost per call and the query latency at which it becomes negligible,
not as one percentage measured against a local, nearly free query. On the
owner's machine (`P5-local.md`), T3 and T4, whose base p50 there is 1592.7 and
1593.1 µs, were already the closest to the target, which is the same effect. These implied

### Reading

- **DCP's recall is 1.0 at every level, on every key, live and in replay.** Its
  nodes and run edges are exact. Its precision drops below 1.0 on dataset
  edges and provenance, and **every extra item it reports is a distractor
  read** (the "Explained by a distractor read" column equals "DCP extras" on
  every key, with no unexplained extra). This is the job-level parenting
  limitation, measured rather than designed away: an `INSERT … VALUES` or a
  produce has no SQL naming its sources, so DCP parents it to every earlier
  read of the job, including one whose values were never used. `INSERT …
  SELECT` statements are exact, because there the statement names its
  sources.
- **The dataset-level baseline** keeps recall 1.0 but loses much more
  precision on provenance: reachability over dataset edges follows every
  producer of a fan-in topic, not the record actually consumed, and every
  distractor edge DCP's dataset edges carry.
- **OpenLineage's core model** (inputs × outputs per run) loses the most
  precision on both levels, through multi-statement jobs, fan-in topics and
  distractor reads alike.
  **It also loses recall**, which the task said would be a bug to investigate.
  Investigated: every miss is explained by a split run. A consumer that reads
  records from two producers adopts each record's trace, so its events carry
  two `trace_id`s, and the P4 bridge maps one OpenLineage run per (trace,
  process): one process becomes two runs, and inputs × outputs cannot connect
  the first record's topic to the row written in the second run. The
  "Explained by a split run" column equals "Missed items" on every key. This is
  a property of the P4 bridge's run mapping combined with OpenLineage's core
  model, not a capture bug and not a property of OpenLineage alone: a mapping of
  one run per process would not lose this recall, but would join even more
  inputs to outputs. The mapping is a P4 decision and was not changed.
- **With the `dcp` facet, OpenLineage matches DCP** exactly, recall 1.0
  included: the facet carries DCP's events, and the reader rebuilds DCP's
  graph from them.
- **The hand-written keys still score exactly as before**, live and in replay:
  the replay, live and adversarial sections of `P5-p51-ground-truth.md` match
  `P5-local.md` row for row (only the run-id line differs), with consumption
  now by exact offset (B1).

## 11. Decisions made

- **Branch.** The work is on `p5.1-hardening`, branched from the latest `main`,
  as the task and the session's instructions say.
- **Every measured comparison is a same-machine pair, back to back**, and the
  final code got its own fresh pair (`p51-before-final`, `p51-after-final`)
  because O3 was revised after the first after-run. Both pairs are committed
  and reported; neither replaces the other.
- **The machine's other Pythons were measured too.** The CPU stage ran on
  every interpreter here: 3.10, 3.12 and 3.14 in the first pair (the CI
  matrix), 3.11 and 3.13 as their own cpu-only pair, and all five in the final
  pair.
- **A1, pins:** exact versions, with environment markers where Python 3.10
  cannot install the newest release; one `pip` command installs the three
  packages and the extras so the constraints apply to all of it; `run.py`
  records mismatches and never fails on them.
- **A2, diagnostics without behaviour change:** `null://` builds every event
  and does nothing with it, not even serialise it, so `capture-null` measures
  capture and construction; `DCP_CAPTURE=off` (also `0`, `false`, `no`, any
  case) leaves the wrappers installed and calls straight through, skipping the
  SQL comment too; `wrap-only` uses it with `null://`. Both are also
  documented as an operational kill switch and a diagnostic sink.
- **A2, the profile** ranks the top 15 functions reached from DCP's psycopg
  wrapper (the whole call path, which includes the original `execute`) and,
  separately, DCP's part alone (not through the original `execute`), because
  the whole-path ranking is dominated by psycopg's own work. Timings from the
  profiling round are never used.
- **A2, attribution is computed by code**, from the per-round values the
  harness now keeps: by p50 (what A3 asks) and by the implied mean cost per
  call (which, unlike medians, adds up).
- **A3:** the ~40 µs is named as capture and construction on the real path
  (§4).
- **A4:** O1 as specified, as a second cache level so the hit path is
  untouched; O2 because capture + construction is attributed ≥ 10 µs; O3
  because the file write is attributed ≥ 10 µs, then revised on its measured
  result. Nothing else was optimised (§5).
- **A5:** post-import hooks, lazy sqlglot, and lazy package names. **The
  in-process launcher was cut**, first in the task's cut order, for a reason
  other than budget: it cannot preserve start-up semantics fully. A
  user's `sitecustomize` and `.pth` files would run in the launcher process
  before `sys.argv` names the script (so they would see the wrong `argv`),
  tracebacks would carry the launcher's frames, and interpreter flags would
  have to be re-parsed. What it would save is one interpreter start (the
  `python` row of §6) and the wrapper's own imports.
- **B1:** produce steps append to a run manifest (`manifest.jsonl` in the
  workload's run directory) from the delivery callback; consume steps assign
  the named record's partition at its offset and fail loudly unless the
  message is that record at that offset. The run record keeps the manifest.
- **B2:** the generated keys live in `benchmarks/ground_truth/generated/*.json`,
  outside the `*/expected_graph.json` pattern, so the hand-written keys' replay,
  live run and pinned `score.py` output never see them.
- **B3:** the `scale` stage replays every generated key and, where the
  services are, runs them live (quick mode: `scale_s01` only); the ten seeds
  are micro-averaged together and `scale_large` is reported on its own; every
  DCP extra is checked against the distractor reads and every miss against
  split runs, by code.
- **A7/B4:** the CI `live` job installs the pinned environment; its quick mode
  picks up the L tiers, the ablations, the profiling round and the `scale`
  stage automatically. The unit CI (including the `windows` job) replays every
  generated key in `benchmarks/tests`.
- **A8:** checked, nothing published (§12, assumption 21).
- **Line endings (P5 rule 5):** the generated keys and the two new renderer
  fixtures are `-text` in `.gitattributes`; the owner's schema line and the
  existing rules are unchanged.

## 12. Assumptions — needs review

Judgement calls made without asking; the more conservative option each time.

**Measurement**

1. **L tiers' literals.** L1 inlines the call's number as the id, so ids above
   4 match no row, as such ids would in a real script; L3 inlines the number
   and a value derived from it; L5 inlines `-n` where T5 binds `0`, so it varies
   on every call and still keeps every row. Each call of a process uses a new
   number, warm-up included, and the texts are built before the timed loop.
2. **The ablations also run for Kafka** (`wrap-only`, `capture-null`), so the
   Kafka cost can be attributed too. Kafka has no `http-down` or
   `file+sqlcomment`, so its enqueue is measured against the live backend
   (`http − capture-null`) and its file write against `capture-null`.
3. **`wrap-only` uses the `null://` sink** as well as `DCP_CAPTURE=off`; with
   capture off the sink is never called, and `null://` makes certain nothing
   could be written.
4. **The new configurations go after P5's five in the round order**, so P5's
   relative order is unchanged.
5. **The profiling round uses the mode's warm-up and call counts**, on T1 and
   L1, once per instrumented configuration, after the timed rounds.
6. **Two start-up variants were added** (a program that imports psycopg and
   confluent-kafka, plain and under `dcp-instrument`), because the hooks only
   help programs that do not import a library, and the report must not imply
   otherwise.
7. **The comparison renderer's fixed-cost table** uses the after run's point
   estimate of the implied cost and 1, 10 and 100 ms as representative query
   latencies, chosen before looking at the results.
8. **"Every Python available" includes 3.11 and 3.13**, measured as their own
   cpu-only pair (the first pair had already run on the CI matrix's three).

**Optimisations**

9. **O1 stores a result under the normalised key only when sqlglot parsed the
   text**, and texts it cannot read for certain are their own key. If sqlglot
   could parse one literal variant of a statement but not another, the
   unparseable variant now gets its parseable sibling's tables, where before it
   got none: a recall gain that only appears on text sqlglot cannot parse. No
   test corpus contains such a pair.
10. **O1 uses NUL as the placeholder**, which libpq can never send, so no real
    query text can collide with a key.
11. **The synchronous file sink is the default** (O3 revised), because it was
    measured faster here and keeps write-before-return durability. The
    asynchronous sink stays, opt-in, as `file://path?sync=0`; `?sync=1` is
    accepted for the synchronous mode. Only an exact trailing `?sync=0` or
    `?sync=1` is parsed, so Windows paths are never read as URLs.
12. **O2 caches per connection object** and assumes, as the task states, that a
    psycopg connection's host, port and database never change.
13. **`import dcp` is lazy** (PEP 562), part of A5's start-up work: every public
    name still resolves, `from dcp import init` still works.

**Generated ground truth**

14. **Values are computed by the generator from the seeded rows** and written
    into the SQL text and the record name (`r007=412`); the live programs send
    exactly that. What DCP sees on the wire is the same as for a program that
    computed the value at run time, and the truth is the same data flow.
15. **Not generated:** a job reading a table another generated job wrote
    (store-mediated lineage, out of v1 scope, and Postgres reads carry no
    parents), and a consumer reading two records from one topic (job-level
    parenting keeps the latest read per dataset, a documented v1 limitation).
    Generating them would rediscover known gaps rather than measure precision.
    Both are noted as follow-ups.
16. **All writes of a script job derive from all the tables it uses**; a script
    whose different outputs use different subsets of its reads would add a
    further, real source of job-level imprecision that is not generated here.
17. **Job mix and sizes** (40% script, 25% consumer, 25% multi-statement, 10%
    notebook; 3 rows per source table; a third as many source tables as jobs;
    a tenth as many topics) were fixed before any scoring.
18. **Notebook names end in `.ipynb` and run in real kernels live**, as the
    hand-written notebook key does.
19. **The micro-average pools the ten 30-job seeds; `scale_large` is reported
    on its own**, so the one large key cannot dominate the seeds' average.
20. **OpenLineage's core-model recall loss is reported, not fixed**: it comes
    from the P4 bridge's run mapping, a P4 decision outside P5.1's scope.

**Other**

21. **A8 (PyPI), checked on 2026-10-03 through the PyPI JSON API:** `dcp` is
    **taken** (an unrelated, active project described as "A DCP SDK"; at the
    lookup, its latest release was 3.4.3, uploaded 2026-04-23). `dcp-backend` and `dcp-openlineage` returned
    404 (no such project). Since the SDK's own name is the problem, the owner
    should choose a family of names together. Candidates that also returned 404:
    `dcp-lineage`, `dcp-capture`, `dcp-instrument`, `wiretap-dcp`,
    `wiretap-lineage`, `lineage-dcp`, `dcp-transport-lineage`. Taken: `dcp`,
    `dcp-sdk`, `pydcp`, `wiretap`. A 404 means no project of that name today; PyPI
    can still refuse a name at upload. Nothing was registered or published.
22. **A0 quotes the owner's run as committed.** `P5-local.md` records "Working
    tree dirty: True"; its numbers are quoted as they are.
23. **The scale stage's live half ran in full mode here** (every generated key);
    quick mode runs `scale_s01` only, as B4 asks.

## 13. Known limitations and follow-ups

- **Throughput:** still not met on sub-millisecond queries (§7). The fixed cost
  per call is the useful statement; reducing it further means less Python work
  per event (IDs, timestamps, capture's own logic), not moving it to a thread.
- **The SQL comment and the HTTP enqueue** are each attributed above 10 µs on
  some tiers and were not optimised (§5).
- **The gap between 4a and the real path** (§4) is named as capture on the real
  path, but not explained function by function; a lower-overhead profiler
  (sampling) would say more than cProfile.
- **OpenLineage export splits a consumer that joins two traces into two runs**
  (§8). A future bridge mapping could keep one run per process and carry the
  traces in the facet.
- **Generated keys do not exercise** store-mediated chains, two records from one
  topic in one consumer, or per-output subsets of a script's reads (§12,
  15–16).
- **`dcp` is taken on PyPI** (§12, 21).
- Unchanged from P5: store-mediated inference is not done; the `dcp` facet grows
  without bound in a long run; batch `consume()` adopts the last record's
  trace; worker-thread reads do not parent later writes; `executemany()` and
  `copy()` are not intercepted; `SerializingProducer`/`DeserializingConsumer`
  are not covered.

## 14. Owner runbook (Windows PowerShell)

> **Warning: live seeding is destructive.** `run.py`'s `live`, `adversarial`,
> `scale` and `overhead` stages **drop and re-create** the tables `orders`,
> `refunds`, `summary`, `refund_summary` and `daily_revenue`, and every
> `gen_src_*` and `gen_out_*` table, in your **`dcp`** database, and **delete
> and re-create** the Kafka topics `enriched_orders`, `overhead_bench` and every
> `gen_topic_*`. Don't point them at data you want to keep.

Prerequisites, as for P5: your Docker Postgres on `localhost:5432` with user
`postgres` and a database `dcp`, and Kafka 3.8.0 on `localhost:9092`
advertising `localhost:9092`. From the repository root, on `p5.1-hardening`
(or `main` once merged):

```powershell
# 1. A clean tree, so the result records a clean commit
git status                                    # nothing to commit
git pull

# 2. A fresh virtualenv with the PINNED environment (one pip command, so the
#    constraints apply to the three packages too). Python 3.14 as before.
py -3.14 -m venv .venv-p51
.\.venv-p51\Scripts\Activate.ps1
pip install -c benchmarks/constraints.txt -e "./sdk-python[dev]" -e "./backend[dev]" -e "./bridges/openlineage[dev]" -r benchmarks/requirements.txt
python -m ipykernel install --user --name python3

# 3. Configuration
$env:DCP_PG_PASSWORD = "<your postgres password>"   # default is dcp
$env:DCP_BENCH_KAFKA_VERSION = "3.8.0"               # recorded as "declared"

# 4. The run: full mode, every stage, scale included. Close heavy programs first.
python benchmarks/run.py --label local-p51
#    Optional: --cpu-python C:\path\to\another\python.exe (repeatable)
#    Writes benchmarks\results\local-p51\results.json and docs\results\P5-local-p51.md.
#    Check the "Pinned versions" row: a mismatch is recorded, not fatal.

# 5. Commit the generated file, untouched
git add docs/results/P5-local-p51.md
git commit -m "P5.1: owner's full-mode results (local-p51)"
git push
```

Every stage must show `ran` in the file's "Stages" table. `local-p51` is a
single run of the final code, not a before/after pair: compare it with
`P5-local.md` only as "the same machine, P5 then P5.1", knowing that P5.1 adds
tiers and configurations P5 did not run. If you also want a same-machine
before/after pair on the dedicated machine, check out `9cf6e7d` in a separate
worktree, install it into a separate virtualenv the same way, run
`python benchmarks/run.py --label local-p51-before --only cpu,overhead` there,
then `--label local-p51-after --only cpu,overhead` on the final code right
after, and render
`python benchmarks/render.py --compare --title "P5.1 on the owner's machine" benchmarks/results/local-p51-before/results.json benchmarks/results/local-p51-after/results.json docs/results/P5-local-p51-comparison.md`.
