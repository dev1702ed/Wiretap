# P4 results: the OpenLineage bridge

Branch `p4-openlineage-bridge`. Task spec: `docs/tasks/P4.md`.

## 1. Summary

P4 adds `dcp-openlineage`, a batch bridge that translates recorded DCP events into
OpenLineage RunEvents. Every event it emits validates against the official
OpenLineage schema, vendored at release tag 1.53.0. It can write them to JSONL or
POST them to Marquez's `/api/v1/lineage`. One OpenLineage run is one process's
share of one DCP trace. The translation is deterministic and does not depend on
event order. Each run's `COMPLETE` event carries a `dcp` run facet holding the
DCP events behind the run, so the round trip DCP → OpenLineage → DCP gives back
the same events and the same backend graph.

The measurement: read through OpenLineage's **core run model** (inputs × outputs
per run), DCP's two precision gains disappear, as predicted.

- **Within one job** (`job_granularity`, a new answer key written by the project
  owner): dataset edges drop to **2/4 precision**, and each output's provenance
  to **1/2**.
- **Across jobs** (`topic_fan_in`): `daily_revenue`'s provenance drops to **2/3**.

With the `dcp` facet, a DCP-aware reader gets every number back to **1.0**. On
`dark_zone`, which does not discriminate, everything is 1.0 either way. DCP's own
graph scores 1.0 on the new `job_granularity` key, so no DCP bug was found. All
of this comes from replay with faked I/O, not live runs.

The seven P3 review fixes (Part F) landed first, one commit each. CI now lints all
four Python directories, pins ruff 0.16.9, and tests Python 3.10, 3.12 and 3.14.
Every CI step passes locally on all three. The Marquez example is written but
**unverified**: there was no Docker here.

Nothing was cut from scope.

### Reading

- **DCP itself** scores 1.0 at every level on all three workloads, including the
  new `job_granularity`. Each `INSERT … SELECT` is captured as a read and a write
  whose parent is the read in the same statement, so `summary` derives from
  `orders` alone.
- **OpenLineage, core run model, `job_granularity`:** `split_loader.py` becomes one
  run with inputs `{orders, refunds}` and outputs `{summary, refund_summary}`.
  Read as inputs × outputs, that is 4 edges where the truth has 2 (precision
  **2/4**). The two spurious edges are exactly the cross pairs, so each output's
  provenance gains the other input (**1/2**). This is the within-job loss.
- **OpenLineage, core run model, `topic_fan_in`:** the dataset edges survive (3/3),
  because each run there has one input and one output. Provenance does not:
  `daily_revenue` picks up `refunds` (**2/3**), the same over-approximation as the
  P3 dataset-level baseline. OpenLineage has no way to say which producer run's
  record the consumer run read. This is the cross-job loss.
- **With the `dcp` facet:** rebuilding the backend graph from the facets and
  asking `upstream()` gives **1.0** everywhere. The facet carries everything the
  core model drops.
- **`dark_zone`** is 1.0 in every row. It has one input and one output per run and
  one producer per topic, so nothing is lost. It is a sanity check, not a
  discriminating workload.
- Recall is 1.0 in every row: the core run model over-approximates and never
  misses an edge.

### Caveats, stated plainly

- **Replay with faked I/O, not a live run.** The events come from DCP's real
  capture code (`benchmarks/ground_truth/harness.py`) with faked cursors and Kafka
  messages. Live replay is P5.
- **The comparison is against OpenLineage's core run model.** OpenLineage also
  has an optional column-lineage facet. When an integration populates it, it can
  carry finer-grained lineage than inputs and outputs, including which input
  columns feed which output columns, and so could avoid the `job_granularity`
  loss. The bridge does not populate it (DCP has no column-level lineage). These
  numbers say what the core model can express, not what every OpenLineage
  integration emits.
- **Three small workloads.** They were each built to isolate one effect. They show
  that the losses exist and where they come from; they say nothing about how
  common those patterns are in real pipelines.
- **Marquez's own reading is not measured.** The "openlineage" rows apply the
  inputs × outputs reading in `reconstruct.py`. Marquez draws its graph from the
  same inputs and outputs, but this was not checked against a running Marquez.

## 6. Decisions made

- **The mapping was implemented as specified** in the task: one run per
  (`trace_id`, `job.host`, `job.pid`, `job.name`), `runId` by `uuid5` over the
  `|`-joined key, job namespace `dcp://{host}`, `START` at the earliest `ts` and
  `COMPLETE` at the latest. Recorded in `docs/decisions/openlineage-mapping.md`,
  including why trace → run was rejected.
- **The vendored schema is the real one.** It was downloaded from the OpenLineage
  repository at tag 1.53.0, the newest release at the time, and a test pins its
  sha256. The spec version it defines is 2-0-2.
- **Output order:** runs are sorted by start time, then job namespace, job name,
  and runId; each run's `START` comes before its `COMPLETE`. Identical duplicate
  events count once, so re-ingested events do not change the output.
- **Inputs and outputs are on both `START` and `COMPLETE`.** The facet is on
  `COMPLETE` only, as specified.
- **The transport is fail-loud.** It is a batch tool, so unlike the capture path
  it raises and the CLI exits non-zero. A failed event stops the run, so later
  events are not sent out of order.
- **The scorer finds the bridge on its own.** `score.py` imports
  `dcp_openlineage` and falls back to `bridges/openlineage` on `sys.path` when it
  is not installed. The bridge has no dependencies, so this always works, and
  `test_backend_score.py` needs no extra skip.
- **The OpenLineage numbers are pinned twice.** `score.py` prints them, and
  `test_bridge_roundtrip.py::test_ground_truth_scores` asserts them from the same
  harness: the facet rebuilds every key exactly, and the core reading gives the
  over-approximations shown above.

## 7. Assumptions — needs review

Each of these was a judgement call made without asking. The conservative option
was taken each time.

1. **The `dcp` facet carries more than the task's sketch.** The sketch had
   `_producer`, `_schemaURL`, `trace_id` and `events[]` with `edge_id`, `op`,
   `dataset` and `parent`. The facet also carries `dcp_version`, the run's DCP
   `job` (`name`, `host`, `pid`), and each event's `ts` and, when present,
   `columns`. Without them the round trip could not rebuild the original
   envelopes exactly (the `runId` is a hash and cannot be inverted). The facet
   schema forbids any other property.
2. **A missing `job.host` becomes job namespace `dcp://unknown-host`** rather than
   failing the translation. The envelope schema requires `host`, so this only
   matters for hand-made input.
3. **Timestamps:** `eventTime` is normalised to UTC ISO 8601 with `+00:00`. A
   trailing `Z` is accepted, a naive timestamp is taken as UTC, and an
   unparseable `ts` makes translation fail with `ValueError` rather than being
   skipped.
4. **`--events` and `--db` may be given together.** The task's usage line shows
   `--events FILE.jsonl [--db PATH]`. The CLI requires at least one, and with both
   it translates the union. `--db` refuses a path that does not exist instead of
   letting SQLite create an empty database.
5. **408 and 429 are retried** as well as 5xx and network errors. They are
   transient by definition. Every other 4xx fails at once.
6. **One POST per OpenLineage event**, in order. Marquez's `/api/v1/lineage` takes
   one event per request.
7. **F1: the `test_patch_psycopg` monkeypatch target moved** from `_classify` to
   `_classify_parts`, because `_capture` now calls the parts helper. The test
   still checks the same behaviour; `_classify` and `test_classify.py` are
   unchanged.
8. **F1: quoted names that contain dots are still ambiguous once joined.**
   `"a.b"` becomes `dcp.public.a.b`, which a reader splitting on dots would take
   as four parts. The decision to prefix the database is now made on the parsed
   structure, so the prefix itself is right; only the joined string stays
   ambiguous. The envelope has no field for name parts, and schema changes are
   out of scope.
9. **F2: the drop count is inherited by a forked child.** The child starts with the
   parent's count at fork time, so it is not reset to zero. Events still in the
   parent's queue at fork time are dropped from the child's copy without being
   counted as the child's drops, because the parent still sends them.
10. **F4: "more than one distinct record" means distinct event content.** Two
    records with the same `edge_id` and byte-identical events (after canonical
    JSON) are a duplicate, not a conflict.
11. **Python 3.14 is tested locally as 3.14.8**, not the pre-installed 3.14.0rc2,
    which breaks pydantic (§5).
12. **Marquez example details**, none verified: image tags `marquezproject/marquez:0.51.1`,
    `marquezproject/marquez-web:0.51.1` and `postgres:14` (all confirmed to exist
    on Docker Hub); API on 5000, admin on 5001, web UI on 3000; search disabled
    (`SEARCH_ENABLED=false`) so no OpenSearch container is needed; a database
    healthcheck replaces Marquez's `wait-for-it.sh`. The example scripts default
    to `postgresql://postgres:postgres@localhost:5432/dcp` and `localhost:9092`,
    overridable with `DCP_PG_DSN` and `DCP_KAFKA`, because your scratch scripts'
    connection details are not in the repo.
13. **The example scripts are new files**, named `nightly_enrich.py` and
    `warehouse_loader.py` after the dark-zone story, not copies of your
    `scratch_produce.py` / `scratch_consume.py`, which are not in the repo. A
    separate, uninstrumented `seed.py` creates the tables, so setting up the data
    does not appear as lineage. The producer reads `SELECT * FROM orders`, so an
    existing `orders` table with other columns still works.

## 8. Known limitations and follow-ups

- **The Marquez example has not been run.** See §9.
- **Marquez does not draw edges from the `dcp` facet.** It stores the facet and
  shows it as JSON on the run; its graph still comes from inputs and outputs. The
  facet's precision is available only to a DCP-aware reader, such as
  `reconstruct.dcp_events` plus the backend graph.
- **`COMPLETE` is the end of the observed window**, not a process exit. Exporting
  a long-running consumer again after more events gives the same `runId` with a
  later `COMPLETE` time. DCP never emits `FAIL` or `ABORT`.
- **No batching or streaming in the transport.** It POSTs one event at a time.
  That is fine for recorded files; a live sink (out of scope) would need more.
- **No column-lineage facet.** DCP has no column-level lineage in v1.
- **Run granularity follows processes, not the scheduler.** A long-lived process
  that handles many traces becomes many runs of one job.
- **Live replay is still P5.** The P4 numbers, like P3's, come from faked I/O.
- The P3 follow-ups not in Part F (for example zero-code auto-instrumentation,
  decision 6) remain open.

## 9. Manual verification for the user

Full steps: [`examples/marquez/README.md`](../../examples/marquez/README.md). In
short, in Windows PowerShell from the repository root:

1. **Start Marquez:**
   `docker compose -f examples/marquez/docker-compose.yml up -d`. The API is on
   **http://localhost:5000**, the web UI on **http://localhost:3000**. Marquez's
   own Postgres publishes **no** host port, so it does not clash with your
   Postgres on 5432. `Invoke-RestMethod http://localhost:5000/api/v1/namespaces`
   should answer.
2. **Record:** create a venv, then
   `pip install -e "./sdk-python[postgres,kafka]" -e ./bridges/openlineage`. In
   `examples/marquez`, run `python seed.py` (not instrumented), then
   `python nightly_enrich.py`, then `python warehouse_loader.py`. The last two
   record with
   `dcp.init(emit="file://dcp_events.jsonl")`. Set `$env:DCP_PG_DSN` and
   `$env:DCP_KAFKA` first if your connection details differ from the defaults.
3. **Send:**
   `python -m dcp_openlineage --events dcp_events.jsonl --post http://localhost:5000`.
   Against an empty topic it should print
   `posted 4 OpenLineage events (2 runs) to http://localhost:5000`; older records
   on the topic add runs.
4. **Look:** open http://localhost:3000 and choose the namespace
   `dcp://<your computer name>`. You should see the two jobs, `nightly_enrich.py`
   and `warehouse_loader.py`, connected through the Kafka dataset
   `enriched_orders` (namespace `kafka://localhost:9092`):
   `orders` → `nightly_enrich.py` → `enriched_orders` → `warehouse_loader.py` →
   `order_totals`. Each run's `COMPLETE` event shows the `dcp` facet as JSON.

If any step fails, the step number and the error are what is needed to fix it.
