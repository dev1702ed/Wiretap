## 0. Why P5.2 exists

These results go into a paper next. A review of P5.1 found two ways in which the
evaluation is unfair, both in DCP's favour. P5.2 removes both. **Its goal is a
fair comparison, not better numbers for DCP.** Both fixes are expected to make
DCP's comparison look *less* favourable in places. That's intended.

**Problem 1 — the OpenLineage baseline is partly an artefact of our own bridge.**
P5.1 reports OpenLineage-core recall below 1.0 at scale (dataset edges 0.955,
provenance 0.945 over ten seeds) and explains the misses as "split runs". The
split is caused by **our** bridge. It maps one OpenLineage run per (trace,
process), so a consumer that joins two traces becomes two runs. A real
OpenLineage integration reports **one run per process**, with all of that
process's inputs and outputs. The paper's baseline must model what OpenLineage
would actually report.

**Problem 2 — the scaled benchmark excludes DCP's known failure modes.** P5.1's
generator deliberately did not generate:

1. a consumer that reads **several records from one topic** and writes using
   all of them (job-level parenting keeps only the latest read per dataset);
2. a job that reads a table **another generated job wrote** (store-mediated
   lineage: Postgres reads carry no parents).

Both are documented v1 limitations, and both are cases where DCP's **recall**
should drop. A benchmark that never exercises its own tool's weaknesses is
selection bias. They must be measured, and reported **separately and clearly**,
never mixed into the main scale results.

**Problem 3 — v1 isn't closed.** The evidence is spread across about twenty
records. The repo isn't release-ready (no version, changelog or citation file),
and the owner's remaining steps are scattered across reports. Part C makes the
repo release-ready and builds a paper evidence pack: canonical tables plus
figures. Part D writes the final v1 report and **one** owner runbook. After this
session, the paper is written from the evidence pack alone.

## 3. Pre-registered expectations — directions, not targets

| Result | Expected |
|---|---|
| OpenLineage core, **per-process**, on the existing scale keys | **Recall 1.0** at every level (no split runs). **Precision equal to or lower than** the trace×process mapping (bigger input × output products) |
| OpenLineage core, per-process, on the hand-written keys | Identical to the current mapping (none has a process that joins two traces) |
| DCP on the stress set | **Recall below 1.0** on provenance (store-mediated chains, multi-record consumers), and on dataset edges where a multi-record consumer's earlier records feed its write. Run edges stay at 1.0 |
| Dataset-level baseline on the stress set | **Recall 1.0 on store-mediated provenance**, since dataset reachability crosses tables. Precision stays below DCP's |
| OpenLineage core, per-process, on the stress set | Recall 1.0; the lowest precision |
| OpenLineage + `dcp` facet on the stress set | Equal to DCP (the facet carries exactly DCP's events), including DCP's recall loss |

If the stress set shows dataset-level lineage beating DCP on recall, **that's a
real, reportable trade-off: precision against recall.** Report it plainly.

## Part A — Per-process OpenLineage mapping

### A1. Bridge option — `bridges/openlineage/`

- Add a run-scope option to `to_openlineage(events, run_scope=...)` and the CLI
  (`--run-scope`):
  - `"trace-process"` — **the default, unchanged**;
  - `"process"` — one run per `(job.host, job.pid, job.name)`.
- In `process` mode:
  - inputs are every dataset the process read;
  - outputs are every dataset it wrote;
  - `runId = uuid5(DCP_RUN_NAMESPACE, …)` over the process key, under a
    **different** name prefix so the two modes can never collide;
  - `START` and `COMPLETE` carry the earliest and latest `ts` across the
    process;
  - the `dcp` facet carries **every** DCP event of the process. It may span
    several traces, so record them as a sorted list `trace_ids`, keeping
    `trace_id` as the first for compatibility. Extend `DcpRunFacet.json`
    **backwards-compatibly**.
- `reconstruct.py` handles both modes.

**Documented limitation (no fix):** two processes with the same job name and the
same pid on the same host — pid reuse — merge into one run in `process` mode.
DCP events carry no process start time. Test that the merge happens as
described, and document it in `docs/decisions/openlineage-mapping.md`. Don't
work around it.

### A2. Case matrix for the mapping — every row needs a test, in both modes

| # | Case | Expected in `process` mode |
|---|---|---|
| 1 | One process, one trace | Identical inputs/outputs to `trace-process`; a different runId |
| 2 | Consumer joining two traces (two producers), then one write | **One run**: the topic as input, the table as output |
| 3 | Long-running consumer handling *N* traces, with a write after each | One run; every input and output |
| 4 | A process with reads only | A run with inputs, no outputs |
| 5 | A process with writes only | A run with outputs, no inputs |
| 6 | The same job name on two hosts | Two runs, two job namespaces |
| 7 | The same job name and host, different pids | Two runs |
| 8 | The same job name, host and pid (pid reuse) | One merged run — the documented limitation |
| 9 | Empty event list | No events |
| 10 | Any permutation of the input events | Identical output (order-independence) |
| 11 | Re-export of the same events | Identical runIds |
| 12 | Round trip: events → OpenLineage → facets → events | The same event set, and the same backend graph |
| 13 | Schema | Every event validates against the vendored OpenLineage schema; every facet against `DcpRunFacet.json` |
| 14 | Both modes over the same events | Same datasets; `process` outputs ⊇ the union of `trace-process` outputs per process |

## Part B — The stress set for DCP's known failure modes

### B1. Extend the generator — `benchmarks/ground_truth/generate.py`

Add two job kinds, controlled by new parameters that **default to off**:

| Parameter | Generates |
|---|---|
| `p_multi_record` | A consumer that consumes **2–3 named records from one topic** — records from different producers, so different traces — and whose written values are computed from **all** of them |
| `p_store_read` | A job that reads a table **written earlier in the same workload by another generated job** (store-mediated), then writes. Allow chains of length 1 and 2 (A writes T1; B reads T1, writes T2; C reads T2, writes T3) |

Requirements:

- **Default-off means byte-identical.** With both parameters at their defaults,
  the generator must reproduce every committed key byte for byte. Test it by
  regenerating all eleven and comparing.
- **The truth is real data flow.** A multi-record consumer's write derives from
  every record it consumed, with their producers' inputs upstream. A
  store-mediated write derives from the table it read **and from everything
  upstream of that table's writer**: provenance is transitive through the store.
- Process order must make every store read happen **after** the write it
  depends on, live as well as in replay. Seed the source tables only, never the
  intermediate ones.
- Distractor reads keep working, combined with both new kinds.
- **Generator version** goes to `1.1`, and keys generated with either new
  parameter on record it. Keys generated with both off stay `1.0`-identical
  (above).

### B2. Case matrix for the generator — every row needs a test

| # | Case | Test asserts |
|---|---|---|
| 1 | Multi-record consumer, 2 records, 2 producers | Hand-written truth: the write's provenance includes both producers' inputs |
| 2 | Multi-record consumer, 3 records, one of them from a producer with a distractor read | The distractor is excluded from truth |
| 3 | Store-mediated chain of length 1 | Provenance crosses the table to the writer's inputs |
| 4 | Store-mediated chain of length 2 | Provenance crosses both tables, transitively |
| 5 | Store-mediated read combined with a distractor read in the same job | The distractor is excluded; the store read is included |
| 6 | Both parameters off | All eleven committed keys regenerate byte-identically |
| 7 | Determinism | Same seed and parameters → byte-identical key |
| 8 | Generated programs | No DCP code |
| 9 | Process order | Every store read comes after its producing write (checked on the generated key) |
| 10 | Live replay of a tiny stress key | Every process exits 0; live scores equal replay scores |

Cases 1–5 use **hand-written expected truth** in the test, on tiny keys, never
truth computed by the generator itself.

### B3. Committed stress keys

- `stress_s01` … `stress_s05`: about 30 jobs, `p_multi_record = 0.15`,
  `p_store_read = 0.25`, other parameters at their defaults.
- `stress_large`: about 100 jobs, same parameters.

Choose the parameters **before** generating, and don't change them after seeing
any score (rule 3 of `P5.2` §2). Each key's `"generated"` block records them.

### B4. Scoring the stress set

- Add a `stress` group to the `scale` stage, reported **in its own section**,
  never pooled with `scale_*` or the hand-written keys. The methods are DCP,
  dataset-level, OpenLineage core (both mappings), and OpenLineage + facet.
- **Extend the explanation check with the new causes:**
  - "multi-record consumer: earlier record's parent dropped (job-level keeps the
    latest read per dataset)";
  - "store-mediated: Postgres read carries no parents".

  Every DCP miss on the stress set must carry one of these two causes, or an
  existing one. Every extra item must still be a distractor read.
- Add a per-cause count table: how many misses each cause produced, per key.
  This is the table the paper's limitations section will cite.

### B5. Run it

```
python benchmarks/run.py --label p52-stress --only scale
```

It must cover both replay and live. Commit `docs/results/P5-p52-stress.md`.
