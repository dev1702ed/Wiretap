## 0. What P5 must establish

The build plan sets a bar, and P5 decides which side of it DCP lands on:

> **Genuine finding:** DCP recovers ≥1 real, useful lineage edge that
> OpenLineage cannot, at < 1 ms p99 added latency.
> **Just a demo:** DCP merely re-derives edges OpenLineage already had.

What already exists: correct capture, with every answer key scored at 1.0, and
measured precision losses in OpenLineage's core model (P3, P4). All of it comes
from **replay with faked I/O**. P5 adds what replay cannot give:

1. **Live evidence.** Real Postgres, real Kafka, and real separate OS processes,
   scored against the same hand-written answer keys.
2. **The adversarial claim, demonstrated rather than asserted.** Scripts and a
   notebook with **zero DCP code in them** are captured, while the OpenLineage
   baseline is shown to be empty.
3. **Overhead numbers** against the < 1 ms p99 and < 2% throughput targets.

**Report what you measure, whichever side of the bar it lands on.** A missed
overhead target, reported honestly, is a valid result. A target met by tuning
the measurement is not.

## Stage 1 — Decision 6: zero-code auto-instrumentation

**Goal:** a script with **no DCP code in it at all** is captured. This turns the
headline claim from "two generic lines" into "no code changes", and it also
removes the Kafka import-order hazard.

**Build**

- A console entry point `dcp-instrument` in the SDK:
  `dcp-instrument python script.py [args…]`, modelled on
  `opentelemetry-instrument`.
  - It runs the given command as a **subprocess**, works on Windows and POSIX,
    and passes the exit code through.
  - It prepends a directory containing DCP's `sitecustomize.py` to `PYTHONPATH`.
- That `sitecustomize.py` runs at interpreter start-up, **before any user
  import**. It:
  1. calls `dcp.init(...)`;
  2. calls `patch_psycopg()`, `patch_kafka()` and `patch_threadpool()`, each only
     if its library is importable;
  3. **chains to any pre-existing `sitecustomize`** further along `sys.path`. Some
     distributions ship one, and shadowing it would break the user's
     environment. This is exactly the trap `opentelemetry-instrument` handles.
- Configuration comes from environment variables:

  | Variable | Meaning | Default |
  |---|---|---|
  | `DCP_EMIT` | Sink | `console` |
  | `DCP_JOB_NAME` | Job name | Script basename |
  | `DCP_PROPAGATE_SQL` | `1` turns on the SQL trace comment | Off |

- Any failure in `sitecustomize` is caught and logged at debug, so the user's
  program still runs — monitor-only.
- Update `spec/README.md` (decision 6 → **closed: yes, via `dcp-instrument`**),
  the README quickstart, and `benchmarks/adversarial/README.md`'s "What decision
  6 changes".

**Tests**

- A subprocess test: an untouched script that imports `psycopg` (fake module on
  the path) and `confluent_kafka` (fake) *before anything else* is captured under
  `dcp-instrument`.
- A pre-existing `sitecustomize` still runs (chaining).
- A broken DCP configuration doesn't stop the user's script.
- The exit code passes through.
- The `DCP_*` variables are honoured.

**Acceptance:** every test passes on every Python available to you.

## Stage 4 — Overhead

**Goal:** measure added latency and throughput loss against the targets,
honestly and reproducibly. Read `benchmarks/overhead/README.md` first.

### 4a. CPU microbenchmark (no database) — your sandbox produces the definitive numbers

- Time `_capture` on a fake cursor with a **discarding emitter** (implement a
  `NullEmitter` in the benchmark, not the SDK). Time `_classify` on its own too,
  to isolate sqlglot's share.
- For each query tier below: 1,000 warm-up calls, then 10,000 timed calls.
  Report p50, p95, p99 and p99.9 in µs.
- Run it on every Python available to you.

**Query tiers (fixed):**

| Tier | Query |
|---|---|
| T1 point read | `SELECT id, total FROM orders WHERE id = %s` |
| T2 join | `orders` joined to `refunds` on `id` |
| T3 insert values | `INSERT INTO summary VALUES (%s, %s)` — exercises job-level parenting |
| T4 insert-select | `INSERT INTO summary SELECT id, total FROM orders WHERE id = %s` |
| T5 analytical | One realistic ~40-line query: at least two CTEs, a join, a window function and an aggregate, over the seeded tables. Write it once and commit it; don't change it after seeing results |

### 4b. Live per-call overhead

**Configurations (fixed):**

| Config | DCP | Sink |
|---|---|---|
| `base` | None | — |
| `file` | `dcp-instrument` | `file://` (tmp) |
| `http` | `dcp-instrument` | `http://` to a **live backend**: `create_app` under uvicorn, one worker, tmp DB, started by the runner |
| `http-down` | `dcp-instrument` | `http://` to a closed port, so the worker is retrying. This tests that `emit()` stays non-blocking under failure |
| `file+sqlcomment` | `dcp-instrument`, `DCP_PROPAGATE_SQL=1` | `file://` |

**Method:**

- Each configuration runs as a **fresh subprocess** per round. Rounds alternate
  configurations in a fixed order (`base, file, http, http-down,
  file+sqlcomment`, repeated) to cancel drift.
- Full mode: **R = 10 rounds × M = 2,000 calls**, with 200 warm-up calls per
  round discarded. Quick mode: **R = 5 × M = 300**, warm-up 50.
- Per call, time `cursor.execute(q, params)` plus `fetchall()` where the tier
  returns rows. Use `time.perf_counter_ns`.
- Throughput: calls per second per round.
- Process start-up is excluded from per-call timing. Report it separately:
  interpreter start-up with and without `dcp-instrument`, in ms.

**Kafka:**

- `produce()` call latency for 1 KB messages, per configuration (`base`, `file`,
  `http`).
- Throughput: 10,000 messages (quick mode: 2,000), then `flush()`.

**Statistics:**

- Per configuration, per tier: p50, p95, p99 and p99.9.
- **Added latency:** `instrumented − base` for p50 and p99, paired by round
  index, with a **95% bootstrap confidence interval** over rounds (10,000
  resamples, fixed seed).
- **Throughput delta %:** same pairing and bootstrap.
- **Verdict per tier against the targets** (< 1 ms p99 added, < 2% throughput):
  met, not met, or inconclusive (the confidence interval straddles the target).

**Backpressure correctness (reported, not a target):**

- Run the `http-down` configuration with a deliberately tiny queue.
- Report `dropped` counts, and confirm per-call latency stays bounded.
