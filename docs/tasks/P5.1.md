## 0. Why P5.1 exists

P5 met the build plan's bar on the owner's machine: a real edge OpenLineage
misses, at < 1 ms p99 added latency on every tier. The < 2% throughput target was
not met. Before any of this goes into a paper, three threats to validity have to
be closed:

1. **The latency claim covers only the cache-hit path.** P5's parse cache is
   keyed on exact query text, and every P5 tier is parameterised, so the text
   repeats. Ad-hoc scripts — the population DCP exists to see — often inline
   literals (`f"... WHERE id = {x}"`). Every such call misses the cache and pays
   the pre-cache cost, which failed the target. **That path is unmeasured.**
2. **The per-call cost is unattributed.** On the owner's machine:
   - `_capture` costs 4.9 µs (T1 p50, cache hit, fake cursor);
   - Kafka `produce()` with the `http` sink adds 8.5 µs;
   - yet a Postgres call adds 50 µs with `http-down` and 81 µs with `file`.

   Roughly 30 µs looks like the synchronous file write and 22 µs the SQL comment,
   but **about 40 µs is unexplained**. Start-up adds about 400 ms per process,
   which matters most for the short-lived scripts DCP targets.
3. **The ground truth is four small hand-written workloads.** Every key scores
   1.0, which a reviewer will read as "toy". It needs a scaled benchmark with
   known truth — including cases where DCP's job-level parenting is *wrong*, so
   its imprecision is measured rather than designed away.

P5.1 closes these three gaps. Part A covers 1 and 2; Part B covers 3. Neither
part's purpose is to make the numbers look better. Where an optimisation is
allowed, its before and after are both reported.

### A2. New measurements — no change to product behaviour

**Cache-hostile tiers.** Each uses a **different literal on every call**, so the
query text never repeats:

| Tier | Query shape |
|---|---|
| L1 point read, literal | T1 with the id inlined |
| L3 insert values, literal | T3 with both values inlined |
| L5 analytical, literal | T5 with one numeric or date literal inlined, varying per call |

Add them to **4a** (CPU microbenchmark) and **4b** (live), alongside T1–T5. Same
warm-up, iteration counts and statistics. Label them "added in P5.1".

**Diagnostic modes.** These are new, but they don't change default behaviour:

- `DCP_EMIT=null://`: a sink that discards events after building them, so event
  construction is included and delivery is excluded. Document it as a
  diagnostic.
- `DCP_CAPTURE=off`: the wrappers stay installed but capture is skipped. This
  isolates the cost of the wrapper itself, and it's also a legitimate
  operational kill switch. Document it as both.

**Ablation configurations (4b, added in P5.1):**

| Config | Measures |
|---|---|
| `wrap-only` | `dcp-instrument` with `DCP_CAPTURE=off`: wrapper and instrumentation cost |
| `capture-null` | `dcp-instrument` with `null://`: wrapper, capture and event construction, on the **real** psycopg path |
| existing `http-down`, `file` | add async enqueue, and the synchronous file write |

**Derived column.** Add to the renderer: **added µs per call, implied by
throughput** = `1e6/throughput_instrumented − 1e6/throughput_base`, paired by
round, with a bootstrap CI. It's computed by code, never by hand. It turns
"throughput %" into the machine-portable fixed cost.

**Profiling round.** One extra round per instrumented configuration, run under
`cProfile`, on T1 and L1 only. It is **not** used for any timing number. Render
the top 15 functions by cumulative time inside the instrumented call path.
cProfile inflates absolute times; use it for attribution, not magnitude.

### A4. Optimisations — attributed costs only, one commit each

**O1. Literal-normalised cache key.** Always in scope, since it targets A2's
cache-miss path.

- Build the cache **key** by replacing literals with a placeholder in one cheap
  pass: numbers, single-quoted strings (including `''` escapes and `E'…'`), and
  dollar-quoted strings. Collapse lists of placeholders (`IN (?, ?, ?)` →
  `IN (?)`).
- **Never touch identifiers** — quoted identifiers included — or keywords.
- On a miss, classify the **original** text and store the result under the
  normalised key. That's safe because which tables a statement touches doesn't
  depend on literal values.
- **Tests:**
  - normalised-key results equal direct classification across the full test
    corpus, every answer key's SQL, and a randomised corpus of literal
    variations;
  - quoted identifiers and dollar quotes survive normalisation;
  - two statements differing only in identifiers never share a key.
- Measure the normalisation pass's own cost in 4a.

**O2 and onwards — only where A3 attributes ≥ 10 µs per call.** Likely
candidates, each conditional on attribution:

- **Per-connection namespace cache.** Compute `(namespace, dbname)` once per
  connection, held in a `WeakKeyDictionary` keyed by the connection, instead of
  reading `connection.info` on every event. A psycopg connection's
  host/port/dbname is fixed for its lifetime.
- **Asynchronous file sink.** Move the write off the caller's thread, using the
  HTTP emitter's background-worker pattern: bounded queue, counted drops,
  fork-safe, `atexit` flush. Keep the current synchronous behaviour available
  as `file://path?sync=1`. The file sink is the benchmarks' event of record, and
  some users need write-before-return durability. Record which mode is the
  default, and why, under Assumptions.
- **Event construction**, if the profile shows it dominating.

### A5. Start-up cost

- **Post-import hooks instead of eager imports.** `sitecustomize` should install
  `sys.meta_path` hooks that patch psycopg or confluent-kafka when — and only
  when — the program imports them, right after the module executes. That keeps
  the Kafka import-order guarantee: the patch lands before a
  `from confluent_kafka import Producer` binding.
- **Import sqlglot lazily**, on first classification.
- **Tests:** the existing `dcp-instrument` tests still pass; a program that never
  imports psycopg never loads psycopg or sqlglot; `from confluent_kafka import
  Producer` binds the patched class; a program importing psycopg *inside a
  function* is still captured.
- **In-process launcher (cuttable).** When the wrapped command is
  `python <script>` or `python -m <module>`, `dcp-instrument` runs the target
  in-process via `runpy` rather than spawning a second interpreter. Preserve
  `sys.argv`, `__main__` semantics and the exit code. Fall back to a subprocess
  for any other command. Test it on Windows semantics too: the `windows` CI job
  runs the tests.

## Part B — Ground truth at scale

### B1. Live consumption by exact offset

Today a live `consume` step reads the earliest record, which only works for
P5's small topologies.

- Each `produce` step records its record's **(topic, partition, offset)** in the
  run manifest, from the delivery callback.
- A `consume` step **assigns and seeks to that exact offset** for its named
  record, then keeps the existing value assertion.
- Every existing workload must score exactly as before, live and replayed.

### B2. Workload generator (`benchmarks/ground_truth/generate.py`)

**Pure Python, and it must not import `dcp`, `backend`, the bridge, or anything
else that computes lineage.** It produces keys in the existing answer-key format
from a seed and parameters, and it derives the expected graph **from its own
construction**: it knows exactly what each generated program does.

**What it generates:**

- Source tables with seeded rows.
- **Script jobs** that read tables and produce records to topics.
- **Consumer jobs** that consume *specific named records* and write tables.
- **Multi-statement jobs** of INSERT … SELECT statements.
- Notebook jobs.
- Fan-in topics with several producers.
- **Distractor reads** (probability `p_distractor`, default 0.3): a job reads a
  table **whose values the generated program then does not use** in what it
  writes.

**Ground truth must be real data flow.** A generated program that writes
`INSERT … VALUES` computes those values from the rows it read — and the expected
graph credits **only** the inputs the values actually came from. So where
distractors exist, DCP's job-level parenting *will* over-approximate, and its
measured precision *will* drop below 1.0. **That is the point: it quantifies a
known limitation. Never configure the generator to avoid it.**

**Committed artifacts:**

- the generator, with a version string;
- the generated keys for fixed seeds: `scale_s01` … `scale_s10` at ~30 jobs each,
  plus one `scale_large` at ~100 jobs;
- a `"generated"` block in each key — generator version, seed, parameters —
  marking it **generated, not hand-written**.

**Tests:**

- regenerating any committed key from its seed reproduces it byte for byte;
- the generator's truth derivation matches **hand-checked** expectations on
  several tiny generated workloads (write those expectations by hand in the
  test);
- generated programs contain no DCP code.

These keys are generated, so rule 3 of `P5.md` §2 ("answer keys are read-only")
applies to the **seeds and generator version**, not to hand edits. Never edit a
generated key by hand.

### B3. Scoring at scale

Add a `scale` stage to `run.py`, in both replay and live modes. For each
generated key it computes the existing per-level precision and recall for:

- DCP run-level;
- the dataset-level baseline;
- the OpenLineage core model;
- OpenLineage with the `dcp` facet.

It reports **micro-averaged precision and recall across all seeds per level and
per method**, plus the per-seed distribution (min, median, max).

Report the generated keys' scores **separately** from the hand-written ones.
Never pool them.

**Expected direction, not a target** — report what you get. DCP scores 1.0
wherever no distractors are involved, and below 1.0 on edges and provenance
involving `INSERT … VALUES` after a distractor read. Dataset-level and
OpenLineage-core lose further precision on fan-in topics and multi-statement
jobs. With the facet, OpenLineage matches DCP. Recall is 1.0 for every method.
If any recall is below 1.0, that's a bug to investigate.

### B4. CI

The unit CI replays the generated keys (fast). The `live` job's quick mode runs
`scale` live on **one** small seed only.
