## 0. Purpose of P4

DCP's graph now matches both answer keys exactly. Most organisations, though, look
at lineage through OpenLineage tooling such as Marquez. P4 translates DCP events
into OpenLineage, so DCP feeds the catalogs people already run instead of
replacing them.

P4 also produces a **measurement**: what survives that translation. OpenLineage's
core run model lists a run's inputs and outputs. It does not say which input fed
which output, and it cannot say which upstream run fed which downstream run.
Translated naively, DCP's two precision gains should disappear:

- within one job, statement-level precision;
- across jobs, run-level provenance through a shared topic.

A DCP-specific run facet can carry the attested edges alongside, so a DCP-aware
consumer can recover them. P4 measures both claims rather than asserting them.

**F1. Fold unquoted identifier case.** Postgres folds unquoted identifiers to

- `Orders` and `orders` resolve to one dataset;
- `"Orders"` stays `Orders`;
- `Sales.Orders` → `sales.orders`;

- re-creates the emitter's locks, in case another thread held one at fork time;
- **clears the inherited queue**, because the parent still owns and sends those

- restarts the worker thread.

`FileEmitter` re-creates its lock too. Add a test that forks a child, has it emit
to a local stub server, and checks that the child's events arrive exactly once.

## Part P — P4: the OpenLineage bridge

### P2. The OpenLineage spec, vendored

Validation must work offline. Vendor the official OpenLineage JSON schema
(`spec/OpenLineage.json` from the OpenLineage GitHub repository, Apache-2.0) at a
**specific release tag** into `bridges/openlineage/schema/`. Record the tag,
source URL and licence in a `README` next to it. The `schemaURL` the bridge
emits must match the vendored version.

If you can't download it, say so in the report and stop the parts that depend on
it. **Never hand-write a substitute and call it the official schema.**

### P3. Mapping — decided; implement as specified

| DCP | OpenLineage | Why |
|---|---|---|
| (`trace_id`, `job.host`, `job.pid`, `job.name`) | **One run** | A DCP trace spans *processes* (producer and consumer share one), but an OpenLineage run belongs to one job. So a run is one process's share of one trace |
| run key | `runId = uuid5(DCP_RUN_NAMESPACE, "\|".join(key))` | Deterministic, so re-exporting the same events produces the same runs. `DCP_RUN_NAMESPACE` is a fixed UUID constant in the code |
| `job.host`, `job.name` | job `namespace = "dcp://{host}"`, job `name = job.name` | The same script on two hosts is two jobs |
| Read events in the run | `inputs`: unique datasets, sorted | |
| Write events in the run | `outputs`: unique datasets, sorted | |
| Dataset `namespace` / `name` | Copied verbatim | DCP's identity model was designed to match OpenLineage's |
| Earliest / latest `ts` in the run | A `START` event and a `COMPLETE` event, both carrying the inputs and outputs | DCP observes no process exit. Document that `COMPLETE` means *end of the observed window*, not that the process finished |

**The `dcp` run facet** goes on the `COMPLETE` event, under the facet key `dcp`:

```json
{
  "_producer": "<PRODUCER_URI>",
  "_schemaURL": "<URL of DcpRunFacet.json in this repo>",
  "trace_id": "...",
  "events": [{"edge_id": "...", "op": "read", "dataset": {"namespace": "...", "name": "..."}, "parent": ["..."]}]
}
```

- `events` lists every DCP event in the run, sorted by `edge_id`.
- Write the facet's JSON Schema to `bridges/openlineage/facets/DcpRunFacet.json`,
  and validate every emitted facet against it in tests.
- `PRODUCER_URI` points at `bridges/openlineage` in this repo.

Translation must be **deterministic and order-independent**: the same set of DCP
events, in any order, yields the same list of OpenLineage events. Sort the
output, and test it over permutations.

Record this mapping, and why trace → run was rejected, in
`docs/decisions/openlineage-mapping.md`. Update `bridges/openlineage/README.md`,
whose leaning ("trace → run") this replaces.

### P4. Modules

| Module | Responsibility |
|---|---|
| `translate.py` | `to_openlineage(events) -> list[dict]`, as in P3 |
| `transport.py` | POSTs each event to `{url}/api/v1/lineage`, with a JSON body. Retries 5xx and network errors with backoff. **Fails loudly** with a non-zero exit: this is a batch tool, not the monitor-only capture path |
| `reconstruct.py` | Given OpenLineage events: (a) the *OpenLineage-implied* dataset edges, i.e. every input × every output of each run, labelled with the job; (b) dataset-level provenance by reachability over those edges; (c) the DCP events recovered from `dcp` facets, so the backend graph can be rebuilt from them |
| `__main__.py` | `python -m dcp_openlineage --events FILE.jsonl [--db PATH] (--out FILE.jsonl \| --post URL)`. `--db` reads the backend's `EventStore`, imported lazily; if the backend isn't installed, print a clear error |
